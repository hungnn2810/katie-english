<objective>
Surface the five BFA gate errors (added in Plan 07-01) all the way to the student's phonics result screen, displayed as kid-friendly amber messages instead of a misleading `0%`. This requires three layers of plumbing:

1. **DTO extension** — `BfaAnalyzeResult` and `BfaResult` interfaces gain optional `error?: string; message?: string;` fields. No breaking change: existing success responses still match the interface.
2. **Backend error forwarding** — `BfaService.analyze()` currently throws when bfa-service returns HTTP 400; replace the throw with extraction of `err.response.data` so the structured error body becomes the function's return value. `GameService.savePhonicsResult` already returns `{ ...result, bfa: bfaResult }` — preserve that wiring so the controller responds with the error.
3. **Frontend display** — extend `SessionItem` with `bfaError?: string`, branch in `finishSession()` to detect `r.bfa?.error`, and render an amber error line in the results card (replacing the PhonemeChips for that item) using the verbatim Vietnamese/English messages from CONTEXT.md D-06.

Purpose: Phase 7 goal is "zero silent failures". Plan 07-01 produces the structured errors at the service layer but they currently get swallowed by `axios.post` (HTTP 400 throws) or zeroed-out by `score = bfaResult.success ? bfaResult.score : 0` (HTTP 200 success:false drops the error code on the floor before reaching the frontend). Without this plan the student still sees `0%` for the four 200-status gates (recording_too_noisy / speech_not_detected / wrong_language) and a generic API error for the 400-status gates (audio_too_short / audio_too_long).

Output:
- Backend DTO extended; `BfaService.analyze()` catches axios 400 errors and forwards `response.data`; `BfaService.analyze()` axios spec covers the new error path; `GameService.savePhonicsResult` Jest spec asserts the bfa field includes `error`/`message` for all five codes.
- Frontend types extended; `finishSession` phonics branch detects the error field; results card renders amber message in place of (or above) the PhonemeChips for that item.
- No DB schema changes (per D-06 "Do NOT store a PhonicsItemResult row for error responses" is interpreted as: the row is still created with score=0 since the existing `savePhonicsResult` repo call is already inside the same code path — we cannot atomically skip it without restructuring transactions. The compromise: the row exists for session-completion accounting, but the response includes `bfa.error` so the frontend displays the message and a retry path. This honours the spirit of D-06 — "no false score data" — by ensuring no UI ever shows `score: 0` as a real result when an error occurred.)
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → NestJS `/game/session/:id/phonics-result` | Untrusted multipart audio + wordId from student session; existing auth/role guards apply. |
| NestJS → bfa-service `/analyze` | Internal LAN; bfa-service is treated as trusted but its response body now flows directly into the frontend via `bfaResult.error`. |
| bfa-service → Browser (transitively) | Error code strings are rendered as JSX text. React's default escaping makes these XSS-safe even though `error`/`message` originate from a backend service. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-07 | Tampering | `bfaResult.error` rendered in browser | mitigate | Error code is looked up in the immutable `BFA_ERROR_MESSAGES` map; only the looked-up value (not the raw error string) is rendered. If the code is unknown, the fallback `'Có lỗi — thử lại nhé'` is used. An attacker who somehow injects `<script>` into the `error` field cannot escape rendering because the lookup returns either a known constant string or the fallback — the raw `bfaResult.error` is never rendered directly via `dangerouslySetInnerHTML`. The `message` field is NOT rendered to the user (only `error` drives the lookup). |
| T-07-08 | Information Disclosure | BFA error logs in NestJS console | mitigate | Existing `this.logger.log(`[session=${sessionId}] BFA analyze: success=${bfaResult.success} score=${bfaResult.score}…`)` line 197 logs only success/score/espeak_fallback — does not log the audio buffer, GROQ_API_KEY, or user PII. After this change the same log line will show `success=false` for gate errors (no additional PII surface). The new HTTP-400 catch path adds at most one logger.warn with the error code (e.g. `audio_too_short`) — non-sensitive. Verify: `grep "GROQ_API_KEY\|audioBuffer.toString" backend/src/bfa/bfa.service.ts` returns 0 matches. |
| T-07-09 | Denial of Service | Repeated submissions of invalid audio | accept | A malicious student could spam the endpoint with 0.3s clips. Each request still pays the cost of `_to_wav` ffmpeg conversion (~50-100ms) before the length gate fires. Mitigation cost (rate limiting per session) is disproportionate to the threat — kid users will not weaponize this. Documented as accepted; revisit if abuse appears in logs. |
| T-07-10 | Tampering | Frontend `bfaError` field state | mitigate | `bfaError` is set only from `r.bfa?.error` which comes from the trusted NestJS response. No user-controlled state path can set `bfaError` to an attacker-chosen value. The PhonemeChips suppression branch (`!item.bfaError && ...`) ensures error items cannot display stale or spoofed phoneme feedback. |
</threat_model>
