<objective>
Build the three new UI surfaces (student login, teacher login, 403, 404) and add the missing student auth guard to `game/layout.tsx`.

Per D-03, each subdomain has its own `/login`. Plan 12-02 created the Route Handlers; this plan creates the visual pages that submit to them. Planner decision for `frontend/app/login/page.tsx`: Keep the combined teacher+student picker as-is — it remains the fallback for local dev where `NEXT_PUBLIC_SUBDOMAIN` is not set, and it still works via localStorage (dual-write from plan 12-02). The combined `/login` page is the app.* teacher login fallback only.

Purpose: Without these surfaces, the subdomain routes either show blank pages (game/* without auth guard), or the middleware redirects loop to non-existent login pages.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /game/login page | Untrusted classCode + name fields submitted; Route Handler (plan 12-02) validates against backend |
| game/layout.tsx → document.cookie | Client-side cookie read; role decoded without signature verify — same pattern as middleware |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-03-01 | Spoofing | game/layout.tsx decodes student-token role without signature verify | accept | Same risk as T-12-01-03. Authorization decision is enforced by NestJS backend on every API call. Layout redirect is a UX convenience, not a security boundary. |
| T-12-03-02 | Tampering | not-found.tsx renders links to all three subdomains | accept | Static links with no user-controlled input. No XSS vector. The NEXT_PUBLIC_*_ORIGIN env vars are server-set at build/start time, not user-controlled. |
| T-12-03-03 | Elevation of Privilege | 403 page "Go to Login" navigates to /login without clearing the bad cookie | mitigate | On arrival at /login the cookie is still present. The login form submits to /api/auth/*-login which will overwrite the cookie on success. Explicit logout/cookie-clear is handled by /api/auth/logout (plan 12-02). The 403 page does not need to clear cookies — it only directs the user to authenticate correctly. |
| T-12-03-04 | Denial of Service | Student login page — no rate limit client-side | accept | Rate limiting is a backend concern. POST /game/auth/login (plan 12-02 backend) is the enforcement point. The frontend form has no special exposure beyond the backend endpoint. |
| T-12-03-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages. All imports (lucide-react, @mui/material, studentTheme) already present in the project. |
</threat_model>
