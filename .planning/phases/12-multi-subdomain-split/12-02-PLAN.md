<objective>
Build the cookie auth layer that bridges the frontend's current localStorage-only auth with the HttpOnly cookies that `middleware.ts` (from plan 12-01) reads for subdomain gating.

Two parallel work streams:

Stream A (backend): Add `POST /game/auth/login` endpoint to NestJS `GameController` — a new public endpoint (no `@UseGuards`) that accepts `{ classCode, name }`, looks up the Class by its `code` field, finds the Student by `fullname` (case-insensitive), signs a JWT via `TokenService`, and returns `{ token, user }`. This is the student entry point: no password, just class membership.

Stream B (frontend): Create four Next.js Route Handlers under `frontend/app/api/auth/` that proxy login requests to the backend and write back HttpOnly cookies (`teacher-token`, `admin-token`, `student-token` — per D-06) using the `next/headers` `cookies()` API. Then update `frontend/lib/auth.ts` and `frontend/lib/admin-auth.ts` to dual-write (localStorage + cookie) so existing sessions keep working. Finally, update `frontend/app/login/page.tsx` and `frontend/app/admin/login/page.tsx` to call the new `/api/auth/*` proxies and redirect via `window.location.href` (cross-subdomain safe per PATTERNS.md).

Purpose: Without HttpOnly cookies, `middleware.ts` cannot read any auth state and every page redirects to login. The dual-write strategy ensures zero regression for anyone with an existing localStorage session.

Output:

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /api/auth/* Route Handlers | Login credentials POST across this boundary; token returned as HttpOnly cookie |
| Next.js Route Handler → NestJS backend | Server-to-server call; credentials forwarded to backend for verification |
| Client JS → document.cookie (dual-write) | Client-side cookie write is visible to JS — acceptable for localStorage parity during transition; HttpOnly cookie from Route Handler is the secure path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-02-01 | Spoofing | POST /game/auth/login — class code + name, no password | accept | Student login by design uses class code + name only (D-03). The class code is a semi-secret shared within the class. Risk is low for a school platform. No PII of consequence is exposed. This matches the product decision recorded in CONTEXT.md D-03. |
| T-12-02-02 | Information Disclosure | Route Handler proxies raw backend error to client | mitigate | Admin login page already suppresses backend error messages ("Invalid email or password" regardless of cause). Teacher and student login pages must do the same — do NOT return the raw backend error body to the browser. Route Handlers return `{ error: text }` but login page components should display a generic message, not `data.error` directly for auth failures (401). |
| T-12-02-03 | Tampering | document.cookie dual-write — teacher-token set with SameSite=Lax (not HttpOnly) | accept | The client-written cookie is a transitional fallback for sessions that predate this plan. The Route Handler sets the HttpOnly cookie which the middleware reads. The non-HttpOnly client cookie is only used by `getToken()` in auth.ts for making API calls from client code (same as localStorage today). Acceptable risk; will be phased out once all sessions have been refreshed via the new login flow. |
| T-12-02-04 | Elevation of Privilege | Student game login bypasses password — attacker guesses class code + student name | accept | See T-12-02-01. Product decision (D-03). NestJS endpoint returns 401/404 for unknown class code or name not in class. |
| T-12-02-05 | Denial of Service | Unauthenticated /game/auth/login endpoint — brute force class codes | mitigate | Document: add rate limiting on this endpoint in a future hardening phase. For now it is inside the school's deployment (not public internet). Acceptable for MVP. |
| T-12-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed in this plan. All imports use existing dependencies (next/headers is built into Next.js, @nestjs/common decorators already present). |
</threat_model>
